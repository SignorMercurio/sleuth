# 报告填充细则与本项目特有约束（步骤 8 写作层）

SKILL.md 步骤 8 写报告前读取本文件：模板逐块怎么填，以及跨章节的本项目约束。句法与文风在 `references/report_style.md`，事实来源与禁止事项在 `references/findings_spec.md`「正式报告写作层使用规则」。

冲突时按以下优先级：findings 中的事实与置信等级 > 用户明确的交付要求 > 模板章节契约 > 本文件的跨章节规则 > 文风样本。不要靠压缩句子同时满足冲突要求；无法消解的冲突回报编排者。

## 模板逐块填充（对应 `assets/report.md`）

先读取 `assets/report.md`，再编辑输出文件。模板 HTML 注释是各章节与指令块局部填充要求的唯一来源，逐块执行但不在正文复述。保留所有 Markdown 标题、frontmatter、`:::` 指令块和 HTML 注释（交付物是渲染后的 PDF，注释不可见）；可以按事件需要增加小节、删除无关字段、空列表项和占位示例，不得删除模板章节。某节没有内容时用一句自然的话说明未发现、无法获取或不适用。不改写为 HTML，不添加 `<span style=...>`/`<font>`/内联 `color` 等视觉样式。

- **Frontmatter**：填写 `date`、`sir-seq`、`version`，模板样值（如 `date: 20250507`）必须替换；`date` 与文件名的事件日期一致（见 `references/report_naming.md`），不填写作当日；`client` 保持占位 `客户名称`，由交付人手工填写
- **封面块**：`::: cover-hero` 仅 `sev` 行按 findings 的最终研判填高危 / 中危 / 低危，不照抄告警级别，不写「无法确认 / 待评估」，缺失时停止定稿并回报编排者；其余固定品牌信息保持原样。`::: cover-meta` 由 frontmatter 自动渲染，禁止手改
- **ATT&CK 矩阵**：保持模板固定版式，不增删或重排，只给 findings「ATT&CK 映射」列出的技术加 `!` 点亮；没有对应槽位的技术不点亮、不借相近槽位，只在覆盖说明用一句交代
- **响应行动状态**：`[x]` / `[/]` 必须来自 findings 的处置进展；写作层新提出的建议只能标 `[ ]`

## 本项目特有约束

- **结论可信度（红线）**：标为「已确认 / 确定」的结论必须已通过步骤 7 的对抗式验证；未通过的按降级措辞写「推测 / 无法确认 / 未观察到」。不确定性的句中写法见 `references/report_style.md`
- **IoC 展示层转义（红线）**：可见文本里攻击者侧 IoC 的 IPv4 和域名只把最后一个点替换成 `[.]`（`1.1.1.1` → `1.1.1[.]1`、`evil.example[.]com`），URL 协议头写成 `hxxp://` / `hxxps://`；受害资产自身的 IP / 域名不转义。命令、检索与内部分析仍用原始值
- **章节分工决定篇幅**：信息放进最合适的一个位置，其他章节不换种说法重复。默认写客户阅读版：结论前置，证据够支撑结论就停止展开。
  - 事件概述用叙事段落回答「发生了什么、影响多大、现在怎样」，管理层 1 分钟读完。
  - 技术分析按观察 → 假设 → 验证 → 结论的真实顺序回答「证据为什么支持结论」，每段只展开一个核心判断。
  - 覆盖说明只交代重要缺口。
  - 响应行动回答「谁还要做什么」，每条以具体动词开头、有明确对象，不写「加强安全意识」这类无执行主体的泛泛建议。
  - 事件总结用自然段收束结论、状态和下一步，不重放时间线、IoC、ATT&CK 或技术分析。
  - 篇幅上限：核心结论 callout 的 body 不超过三句；事件定性、影响范围、处置状态各不超过两句，残留风险按模板 1–3 项每项一句；事件总结不超过三句；单主机、单入口、无横向的简单事件，排查过程不超过 3 段、产品建议至多 1 项。
  - 复杂事件只按已确认的攻击阶段增加小节；除非用户要求深度取证版，不新增长篇附录
- **证据实体有下限**：技术分析「排查过程」中每个已确认的攻击步骤至少完整保留一条 findings 记录的具体证据（类别与写法以 `findings_spec.md`「入侵路径」为准）；接口、URL、路径、账户写具体值，不压缩成「某上传接口」「相关路径」。上限不变：命令流水账、完整日志或低价值排查过程不进报告
- **证据边界只完整展开一次**：同一条限定（如「请求与进程无法关联」「按密钥已泄露处置」）在结论 callout 或技术分析推导处选一个权威位置完整写出，其他章节用短指针（「见核心结论」）或省略；逐字或只换主语的改写也算重复，交稿前按关键短语全文检索确认只展开一处。字段短句、短指针和各章必填落点的一句话不计
- **范围声明一次、只说做了什么**：调查范围限制在排查过程用一句话声明；不逐项罗列未执行的手段，除非某项缺失本身构成客户必须处理的残留风险。「复评条件」类底稿内容不进客户报告
- **未决旁支线索不进正文**：没闭环、落到「需客户确认归属」的旁支（存疑的登录来源、密钥指纹不一致、疑似第二入口）留在 findings；只有构成客户必须继续处理的残留风险时，才提炼成「残留风险」或「证据缺口」里的一条
- **内部工作标识不进报告**：可见正文不得出现 `findings`、工作底稿、底稿章节名、「步骤 7 / 步骤 8」、writer QA、SIREN Client 编号、SIREN 工具名等内部标识（取证来源改写为「只读远程取证」等客户可理解的说法）；输入缺口改写成客户可理解的证据边界。云资源 ID（镜像 `m-*`、实例 `i-*`）默认省略，仅当客户需要据此定位实例执行动作时保留；资产以实例名 + IP 标识
- **历史独立事件不占版面**：与本次入侵无手法或基础设施关联的历史事件不进时间线、ATT&CK 说明和响应行动；必须提及时在资产用途或技术分析一句话带过
- **云端证据写法**：SLS / SAS 类证据写明日志源、时间窗口、最早 / 最新记录与覆盖限制（四类最低覆盖见 `findings_spec.md`「云端证据覆盖」）；进程侧无命令执行证据时也写明进程日志最早覆盖时间，不把「未检出」写成「未发生」
- **证据截图**：图片只引用 findings 记录的截图路径，原样照抄，写法与图注按模板注释；findings 没截图的证据点保留占位 `<报告名>.assets/TODO-<主体>.png`，不造图、不引用不存在的文件。图跟在它佐证的段落后面，正文不因有图省掉证据句
- **文风**：执行 `references/report_style.md`，命中其「出现即改写」清单的句子照单改写
