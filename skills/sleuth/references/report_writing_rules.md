# 报告填充细则与本项目特有约束（步骤 8 写作层）

SKILL.md 步骤 8 写报告前读取本文件。这里集中"模板逐块怎么填"与"本项目特有的报告约束"两类细则；句法/文风/反 AI 腔规则在 `references/report_style.md`，事实来源与禁止事项在 `references/findings_spec.md`「正式报告写作层使用规则」。三者配合使用。

发生冲突时按以下优先级处理：findings 中的事实与置信等级 > 用户明确的交付要求 > 模板章节契约 > 本文件的跨章节规则 > 文风样本。不要靠压缩句子同时满足冲突要求；把无法消解的冲突回报编排者。

## 模板逐块填充（对应 `assets/report.md`）

生成时先读取 `assets/report.md`，再编辑输出文件。模板 HTML 注释是各章节与指令块局部填充要求的唯一来源，逐块执行但不要在正文复述。保留所有 Markdown 标题、frontmatter 和 `:::` 指令块；可以按事件需要增加小节，但不得删除模板章节。某节没有内容时用一句自然的话说明未发现、无法获取或不适用；可以删除无关字段、空列表项和占位示例，但不能删除章节标题。HTML 注释原样保留（交付物是渲染后的 PDF，注释不可见）；不改写为 HTML，不添加 `<span style=...>`/`<font>`/内联 `color` 等视觉样式或字体/背景色。默认写客户阅读版标准报告：结论前置，篇幅由有效内容决定，证据够支撑结论就停止展开；除非用户明确要求深度取证版，不新增长篇附录。

- **Frontmatter**：填写 `date`、`sir-seq`、`version`，模板自带的样值（如 `date: 20250507`）必须替换为本次事件值，不可原样保留；`client` 保持占位 `客户名称`，由交付人手工填写，AI 不改
- **封面块**：`::: cover-hero` 仅 `sev` 行按 findings 的最终研判填写高危 / 中危 / 低危，不直接照抄告警级别，也不写「无法确认 / 待评估」；缺失时停止定稿并回报编排者。其余是固定品牌信息保持原样；`::: cover-meta` 字段由 frontmatter 自动渲染，禁止手改——只需填好 frontmatter
- **ATT&CK 矩阵**：保持模板的固定版式，不增删或重排，只给 findings「ATT&CK 映射」列出的技术加 `!` 点亮
- **响应行动状态**：`[x]` / `[/]` 必须来自 findings 的处置进展；写作层新提出的建议只能标 `[ ]`

## 本项目特有约束

- **结论可信度**：报告中标为「已确认/确定」的结论必须已通过步骤 7 的对抗式验证；未通过的按降级措辞写「推测/无法确认/未观察到」，不要保留确定措辞；不确定性措辞的具体写法（句中标注、双向校准）见 `references/report_style.md`
- **章节分工决定篇幅**：事件概述回答「发生了什么、影响多大、现在怎样」；技术分析回答「证据为什么支持结论」；覆盖说明只交代重要缺口；响应行动回答「谁还要做什么」；总结只收束。信息放进最合适的一个位置，其他章节不换种说法重复
- **按内容单元增减**：简单事件减少证据段和动作数量，复杂事件只按已确认的攻击阶段增加技术分析小节；句法取舍执行 `references/report_style.md`
- **未决旁支线索的去向**：调查中没闭环、最终落到「需客户确认归属」的旁支（如某个存疑的登录来源、密钥指纹不一致、疑似第二入口），不写进客户报告正文，更不要跨章节反复出现——它们属于 findings 工作底稿。只有当它构成客户必须继续处理的残留风险时，才提炼成「残留风险」或「证据缺口」里的一条，其余删除
- **证据边界只完整展开一次**：同一条限定（如「请求与进程无法关联」「按密钥已泄露处置」）在结论 callout 或技术分析推导处选一个权威位置完整写出，其他章节需要时用短指针（「见核心结论」）或省略；交稿前按关键短语全文检索，同一限定出现 3 次以上必须收敛
- **范围声明一次、只说做了什么**：调查范围限制（快速溯源、按客户要求缩小范围）在排查过程用一句话声明；不逐项罗列未执行的手段（未查 ActionTrail、未启用 auditd 等），除非某项缺失本身构成客户必须处理的残留风险。「复评条件」类工作底稿内容不进客户报告
- **内部工作标识不进报告**：可见正文不得出现 `findings`、工作底稿、底稿章节名、「步骤 7 / 步骤 8」、writer QA、SIREN Client 编号等内部标识；输入缺口改写成客户可理解的证据边界，不能写「findings 未提供」。云资源 ID（镜像 `m-*`、实例 `i-*`）默认省略，仅当客户需要据此定位实例执行动作时保留（如在产实例复核项）；资产以实例名 + IP 标识
- **历史独立事件不占版面**：与本次入侵无手法或基础设施关联的历史事件（如数年前的挖矿）不进时间线、ATT&CK 说明和响应行动；必须提及时在资产用途或技术分析一句话带过
- **云端证据写法**：SLS/SAS 类证据必须写明日志源、时间窗口、最早/最新记录与覆盖限制（四类最低覆盖的清单与执行点见 `findings_spec.md`「云端证据覆盖」，写作层照 findings 呈现覆盖或缺口）；进程侧无命令执行证据时也要写明进程日志最早覆盖时间，避免把「未检出」误写成「未发生」
- **文风**：执行 `references/report_style.md`，命中其各「出现即改写」清单（反 AI 腔、非通行措辞）的句子照单改写
- **IoC 展示层转义**：报告可见文本里攻击者侧 IoC 的 IPv4 地址和域名只把最后一个点替换成 `[.]`（如 `1.1.1.1` → `1.1.1[.]1`、`evil.example[.]com`），URL 协议头写成 `hxxp://`/`hxxps://`；受害资产自身的 IP/域名不转义。命令执行、检索过滤、内部分析仍用原始值
- **命令证据**：只把能支撑结论的关键命令和最短输出片段放进对应章节；不要把命令流水账、完整日志或低价值排查过程搬进报告
- **详略边界**：样本分析、ATT&CK 覆盖说明、参考资料都服务于本事件结论；没有样本或无相关资料时保留章节并用一句自然的话说明，不用模板内容凑篇幅
