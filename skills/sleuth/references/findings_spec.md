# Findings 中间文件规范（调查 → 报告的交接层）

每台主机在步骤 1 初始化一份 findings，状态标记「调查中」；每轮取证后补写，步骤 7 核验后标记「已验证」。默认先交付精炼调查结论，不生成正式报告。用户确认进入步骤 8 后，写作层**只以 findings 的已验证事实为来源**，调查上下文或待证问题不能直接进入报告。底稿同时用于断点续查、多主机合并与隔离写作；证据保留可核查原文，篇幅取舍留给写作层。

## 文件命名

```
IR-{YYYYMMDD}-{hostname}-{event_type}[-{event_id}]-client{ClientID}.findings.md
```

报告相关字段含义与 `references/report_naming.md` 一致，ClientID 使用步骤 1 已核对的 SIREN 标识，不用短 hostname 代替资产身份。生成在当前工作目录，单主机也生成（N=1）。本次调查选定路径后保持稳定，即使事件类型细化也不另建一份。

同路径已存在时，先核对底稿中的资产、调查起点及本次是否续查。明确续查则保留原证据与裁决历史，新增采集时间；否则在 `.findings.md` 前加 `-run2`、`-run3` 等未占用后缀，不覆盖旧轮次。未知/缺失 Client ID 的历史报告合并保留原输入路径，以其资产标识区分，不伪造 Client。

findings 是内部工作底稿；正式报告仍按原命名规则只交付一份 `IR-….md`。底稿保留备查，去留由用户决定。

## 逐轮记录与证据完整性

在固定章节前保留一个工作区段：状态、调查起点、最后更新时间，以及 `问题编号 | 待证断言 | 支持/反驳证据编号 | 当前裁决 | 缺口与下一步`。上下文恢复或换主机时先读此区段；未验证内容只留在这里，不混入定稿章节。

证据编号在本底稿内唯一（如 E01），跨主机引用带底稿名或 Client ID。每条证据保留：资产/账号与来源、实际命令或查询、查询时间窗、事件原始时间/时区、采集时间、关键原文、退出状态、是否截断及未读范围。工具提供查询 ID、进程启动时间或会话 ID 时一并记录；来源相同的 API、告警与截图标记同源，不重复算独立证据。

字段不可得就写「未提供」与影响，不猜测时间或完整性。完整性未知、部分返回、失败、未查和完整无命中分别记录；主机证据与委派结果用同一口径。每轮只追加改变问题裁决的证据，重复查询注明状态变化或新范围，仍有效的结果按编号复用。

## 内容结构

按以下固定章节填写；没有内容的章节写「无」，不要删除章节（多主机合并时按章节对位读取）：

1. **主机标识** — 完整 hostname、Client ID、公网/私网 IP、实例 ID、资产用途；云侧另记 UID/地域及映射依据
2. **事件定性** — 一句话定性 + 措辞等级（已确认 / 推测 / 无法确认）+ 报告严重等级（高危 / 中危 / 低危）及一句判断依据，含主要 ATT&CK 技术编号；严重等级是本次事件的最终研判，不直接照抄告警级别
3. **时间线** — 保留影响因果、范围或处置的节点，每条注明证据编号、原始时间及时区；不受正式报告节点上限限制，定稿时区分事件时间与检测/采集时间，不把 ctime 当创建时间
4. **入侵路径** — 按攻击阶段写已验证的步骤，每步附可独立核查的证据记录：优先日志/请求原始行（含时间戳、来源、完整接口路径或 URL、状态码），其次命令及关键输出行、文件绝对路径与时间属性；操作审计、SAS 遥测等结构化来源写出主体、对象、时间等关键字段值。不得用「access 日志可证」「进程链吻合」这类只报来源、不含内容的指针概括代替；没有命令输出时使用对应日志、文件、网络或客户确认记录，不为凑格式补命令。云侧事实有控制台截图时，在该条证据记录下加一行 `截图: <相对路径>（页面 · 账号/站点 · 截取时间）`，规则见「证据截图」
5. **ATT&CK 映射** — `T编号 :: 行为 :: 证据` 列表，只列通过步骤 7 验证门的；§4 已验证步骤体现的技术须在本节有对应条目（反向不要求，本节可含持久化等非路径技术）
6. **IoC 清单** — IP / 域名 / 文件路径 / 哈希 / 账户，记录**原始值**（展示层转义在报告里做）
7. **入口 / 漏洞** — 先写证据支持的初始入口；仅在证据指向漏洞利用时记录类型、受影响组件与版本、CVE（如有）及修复方案来源。凭证滥用、合法工具滥用、配置暴露或社会工程写实际入口并注明「未发现需要绑定的漏洞」；入口证据不足写「无法确认」，不得为完整度强行匹配 CVE
8. **残留风险** — 步骤 6 六个维度的对象与覆盖结果，分别写「已清 / 仍在 / 未观察到 / 未完成 / 不适用」及依据；「已清」需有先前阳性与后续处置/复核记录，不能把缺证据写成清除
9. **处置进展** — 先写当前事件状态，再按抑制 / 根除 / 恢复三个阶段记录已完成、进行中、未开始的动作及依据；`[x]` / `[/]` 只能来自主机证据或客户确认，未取得记录时明确写「未取得处置记录」，不要把建议写成已执行
10. **云端证据覆盖** — 日志源、查询时间窗、最早/最新记录、覆盖限制；告警驱动模式另记 `$sas` 输入范围，直接详情模式记录输入的数字 `Id`，资产 / 实例列表模式记录查询时间窗与完整数字 `Id` 集合，多条结果全部保留；主机侧调查至少按网络外联、进程启动、远程/数据库登录、SAS 告警四类逐项写「覆盖或缺口 + 原因」；未查云端时写明原因
11. **验证结果** — 步骤 7 核验中被降级或删除的断言及原因
12. **证据缺口** — 想查而没查到的项，是报告「覆盖说明」的素材

## 证据截图（可选，只针对云侧事实）

- 步骤 7 验证门过完、findings 定稿前，由编排者委派 `opencli-aliyun-ir` 的控制台截图流程，只截通过验证的承重断言对应的云侧事实（告警详情、ActionTrail 事件、云防火墙/WAF 命中、暴露面配置）；主机侧证据走 SIREN 文本通道，不截图。多主机在全部主机过完验证门后一次委派，文件名带 Client/资产标识。
- 落盘在当前工作目录 `<报告名>.assets/`（报告名按 `references/report_naming.md`，不含 findings 的 Client/轮次后缀），一图对应一条事实。截图挂在它佐证的证据记录下（§4 或 §7–§8），写明路径、控制台页面、账号/站点和截取时间，不单独开章节。
- 截图只佐证已有记录，不计入独立证据源（同源规则见 `references/verification_checklist.md`「因果与孤证」）；截不到不算证据缺口，报告保留图片占位。截图不打码，但不截含登录凭据、Cookie、令牌的页面。

## 正式报告写作层使用规则

- 仅在用户确认生成 / 合并正式报告后进入步骤 8；未确认时停在步骤 7，不复制模板、不创建 `IR-….md`。写作只读规定的输入文件（清单、隔离方式与 QA 见 `references/runtime_compat.md`「报告写作隔离」），不回看调查上下文，不碰 SIREN。
- Findings 是报告的事实边界，不是逐项展开的提纲。写作层按章节职责选择影响定性、影响范围、证据链或客户动作的内容；常规阴性结果合并概括，不影响结论的验证记录和旁支线索留在 findings。
- 只接收状态为「已验证」的底稿；工作区段中的待证断言不得作为事实写入报告。历史 findings 或合并报告无状态字段时，由编排者先按步骤 7 核验再交接，不要求补造采集记录。
- 不得改变事实与措辞等级：「推测」不得升级为「已确认」，IoC 和截图路径不得增删改，时间不得四舍五入到改变先后关系。
- 一般证据缺口不补写、不脑补，在报告对应位置用客户可理解的话说明，并回报编排者决定是否回到步骤 2–7 补查。严重等级、当前事件状态或处置进展缺失时不得定稿，也不得写「findings 未提供」或用「无法确认」填充这些必填字段；先回报编排者补齐。

## 多主机合并规则（多主机委托与合并模式）

合并模式（输入是用户提供的既有 `IR-….md` 报告）下，报告正文视作 findings 等价物，本文件全部规则同样生效：只做重组与改写表述，不得新增事实或升级措辞。

- **排查对象**：每台主机一个 `::: asset` 块（模板原生支持多资产）
- **时间线**：合并为一条统一时间线，节点标注主机名，节点数量上限同报告时间线约束
- **事件定性**：定性针对整个事件；各主机结论明显无关联（无共享 IoC、时间窗、手法）时仍只出一份报告，但在定性中分别陈述并写明「未发现关联」
- **ATT&CK 矩阵**：一个矩阵，任一主机有证据支撑即点亮该技术
- **技术分析**：按主机分小节，另加一节「跨主机关联分析」收纳横向移动 / 同源判断（须已过验证门）
- **响应行动**：合并去重，每条动作标注适用主机并保留各自主机 findings 中的真实状态；全局动作（如封禁攻击 IP）只写一次
- **输出文件名**：按 `references/report_naming.md` 的多主机规则生成
