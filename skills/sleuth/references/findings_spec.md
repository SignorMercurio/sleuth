# Findings 中间文件规范（调查 → 报告的交接层）

每台主机在步骤 1 初始化一份 findings，状态标记「调查中」；每轮取证后补写，步骤 7 核验后标记「已验证」。调查期间 findings 也是用户查看进展的文档，不另建进度文件；默认先交付精炼调查结论，不生成正式报告。用户确认生成报告后，由 dossier skill 的写作层**只以 findings 的已验证事实为来源**，调查上下文或待证问题不能直接进入报告。底稿同时用于断点续查、多主机合并与隔离写作；证据保留可核查原文，篇幅取舍留给写作层。

## 文件命名

```
IR-{YYYYMMDD}-{hostname}-{event_type}[-{event_id}]-client{ClientID}.findings.md
```

| 字段 | 说明 |
|------|------|
| `{YYYYMMDD}` | 事件发生日期（优先告警时间，其次调查时间） |
| `{hostname}` | 受影响主机名（不含域名后缀，特殊字符转 `-`）；云侧事件没有主机时用 `uid{UID}`，WAF 攻击事件可用受攻击域名 |
| `{event_type}` | 事件类型 slug（见下表），未知时填 `unknown` |
| `{event_id}` | 仅用数字告警 `Id` 直接启动的模式一包含；资产 UUID / ECS 实例 ID 的列表型输入不加，即使列表只返回一条告警 |
| `{ClientID}` | 步骤 1 已核对的 SIREN 标识，不用短 hostname 代替资产身份；云侧事件没有 Client 时去掉 `-client{ClientID}` 后缀 |

| 中文事件类型 | slug |
|------------|------|
| Web Shell 后门 | `webshell` |
| 挖矿木马 | `miner` |
| 反弹 Shell | `revshell` |
| 暴力破解 | `brute` |
| 异常登录 | `abnlogin` |
| 权限提升 | `privesc` |
| 数据外传 | `exfil` |
| 勒索软件 | `ransom` |
| SQL 注入 | `sqli` |
| 远程代码执行 (RCE) | `rce` |
| 持久化后门 | `backdoor` |
| AK/STS 凭据滥用 | `akabuse` |
| 其他/未分类 | `unknown` |

生成在当前工作目录，单主机也生成（N=1）。本次调查选定路径后保持稳定，即使事件类型细化也不另建一份。

同路径已存在时，先核对底稿中的资产、调查起点及本次是否续查。明确续查则保留原证据与裁决历史，新增采集时间；否则在 `.findings.md` 前加 `-run2`、`-run3` 等未占用后缀，不覆盖旧轮次。未知/缺失 Client ID 的历史报告合并保留原输入路径，以其资产标识区分，不伪造 Client。

findings 是内部工作底稿，去留由用户决定。正式报告名由 dossier skill 从 findings 名推导（去掉 `.findings` 和 Client、轮次后缀），一次委托只交付一份 `IR-….md`。

## 逐轮记录与证据完整性

在固定章节前保留一个工作区段：当前结论、状态、当前模式、Client 清单、调查起点、最后更新时间、已读 references 的要点，以及排查清单。当前结论用一至三句写目前的定性与影响判断，未过步骤 7 验证门的内容标「推测」或「待证」。头部各项写成 Markdown 列表。每轮写回都更新最后更新时间、当前结论与清单状态。运行环境提供 `case_update` 时，当前结论写入 Case Board 的 `summary`，工作区段不再写当前结论和最后更新时间。上下文压缩恢复或换主机时先读此区段；未验证内容只留在这里，不混入定稿章节。

### 排查清单位置

运行环境提供 `case_update` 时，清单只写 Case Board，工作区段只留一行 `排查清单：Case Board`，不再维护 Markdown 表，避免两份清单不一致。没有该工具时，在工作区段维护 Markdown 表 `编号 | 问题或待证断言 | 维度 | 状态 | 回答 | 支持/反驳证据编号 | 下一步动作 | 受阻原因与已试来源`。调查中途工具不可用时，把 `case_read` 最后读到的未结项转入 Markdown 表继续。

状态只用：待查、进行中、已确认、已反驳、缺口、受阻、不适用；「缺口」写明已试的证据源，「受阻」写明需要谁提供什么。

`case_update` 的状态依次对应 `open`、`active`、`confirmed`、`refuted`、`gap`、`blocked`、`not_applicable`；维度「入口、凭据或权限来源、执行与持久化、横向与关联资产、影响范围与数据、处置状态」依次对应 `entry`、`credentials`、`execution_persistence`、`lateral_assets`、`impact_data`、`response_status`，事件线索引出的待证问题用 `lead`。

写回规则：

- 每轮把变化的项合并成一次调用。新项不传 `id`，以返回的 `Q` 编号继续更新。
- 定性或影响判断变化时，同一次调用传 `summary`：用一至三句写已确定的定性与影响，再用一句写还没验证的内容。未过步骤 7 验证门的内容标「推测」或「待证」。
- Case Board 把 `answer` 显示为发现，把 `next_action` 显示为下一步，`question` 只在展开后显示。`question` 只写问题，不写结果。
- `answer` 写已查实的事实，`confirmed`、`refuted`、`gap` 必填。用一两句陈述谁在什么时间对什么对象做了什么，写具体的主机、账号、路径、时间和数量。
- `answer` 不写「可能」「疑似」「暂未发现」「不能排除」「建议进一步」。查不实的内容不写进 `answer`：保持 `open` 或 `active`，在 `next_action` 写怎么查实。已查实一部分时，新建一项记为 `confirmed`，原项继续查。
- `refuted` 的 `answer` 写排除了什么，以及查过的范围。例如：web-02 在 11-01 至 11-03 的 SSH 登录全部来自堡垒机，没有来自 web-01 的登录。
- `gap` 的 `answer` 写缺什么，以及因此定不了哪个结论。例如：11-01 前的 auth 日志已轮转，入口时间定不了。
- `next_action` 写一个具体动作，写明对象和数据源，`open`、`active`、`blocked` 必填。例如：查 web-02 11-01 至 11-03 的 sshd 日志，确认 10.0.0.5 是否登录。不写「继续排查」。项关闭时不传 `next_action`，SIREN 会清空旧值；还有后续工作就新建一项。
- 按状态补齐字段：`confirmed` 需要实体和 `role: supports` 证据，`refuted` 需要实体和 `role: refutes` 证据；`gap` 需要 `tried_sources`；`blocked` 和 `not_applicable` 需要 `reason`，受阻的 `reason` 写需要谁提供什么或在等哪一项。
- `blocked_by` 只用于 `blocked` 项，填它在等的 `Q` 编号，传入时整体替换。所列项都进入 `confirmed`、`refuted`、`gap` 或 `not_applicable` 后，SIREN 把该项改回 `open`。
- `owner` 取 `lead`、`entry`、`host`、`cloud`，只在 SIREN Case Run 中决定由哪个角色推进该项，角色规则见 `references/runtime_compat.md`「多 Agent 角色」。
- `entities`、`evidence`、`tried_sources` 只传新增内容，SIREN 追加到已有列表。要去掉时用 `remove_entities`、`remove_evidence` 传编号。
- 返回末尾的 `Remaining` 列出未结项，`Dimensions with no items` 列出还没有项的维度，据此选下一项。
- `Repeated direction` 表示同一实体的同一维度已有三项查无结果，且仍有项未结。下一步换证据源或假设；没有新角度就把未结项记为缺口，转查别的项。它只是提示，不限制查询次数，也不是停止条件。
- 证据优先传 run 的 `audit_id` 加 `label`，SIREN 原样保存；`sls -save` 等已落盘文件传 `evidence/<文件>#L<n>-L<m>`；复用时传 `CE` 编号。
- 主机实体用 `kind: host` 加 SIREN Client ID；其他实体用 `ip`、`domain`、`identity`、`file`、`resource`，或复用 `A` 编号。
- 证据链接变化，或项进入、离开 `open`/`active` 以外的状态，或这些状态下的 `answer` 变化时，证据版本递增；已登记的报告随之标为落后。登记由 dossier skill 在报告通过 QA 后完成。
- 校验失败时按错误补齐字段后重试。不要为通过校验改写结论或状态；证据确实不足就保持原状态或记为缺口。

Case Board 的状态不代替步骤 7 验证门；`CE` 编号也不代替底稿证据编号，底稿引用时写全 `CE01`。

### 攻击时间线位置

运行环境提供 `case_update` 时，调查中的时间线只写 Case Board 的 `events`，§3 和 §5 各留一行 `时间线：Case Board`，定稿时按下方快照规则写回。没有该工具时，直接维护 §3 和 §5。

写回规则：

- 事件和清单项合并在同一次 `case_update` 里。新事件不传 `id`，以返回的 `TL` 编号继续更新；`items` 传它回答的 `Q` 编号。`entities`、`evidence` 只传新增内容；`attack`、`items` 传入时整体替换。
- `kind` 只用 `attack`（攻击者动作）、`detection`（客户侧发现）、`response`（客户侧处置）。排查动作不写入事件。
- `from`、`to` 用带时区偏移的 RFC 3339。单一时刻两者相同；只知道最晚时间时只传 `to`，只知道最早时间时只传 `from`。没有任何时间边界时不写事件，把问题留在清单。
- `original_time` 保留来源原文。`precision` 取 `second`、`minute`、`hour`、`day`，按来源实际精度填，不用补零冒充更细的精度。
- `clock_note` 写时区假设、syslog 年份推断和主机时钟偏差。`from`、`to` 不自动校正主机时钟偏差。
- `time_basis` 取 `record`（日志、审计、告警时间戳）、`process_start`、`file_time`（文件 mtime、ctime、birth time）、`derived`（由其他事件推出）。`file_time` 和 `derived` 只能配 `inferred`；有日志佐证时改用日志时间和 `record`。不把 ctime 当创建时间。
- `status` 取 `confirmed`、`inferred`、`withdrawn`。`confirmed` 需要实体和 `supports` 证据；`inferred` 需要证据和 `reason`；`withdrawn` 需要 `reason`，用于被推翻、重复或误写的事件。事件不能删除。
- `attack` 只用于 `kind: attack`，每条传 `tactic` 和 `technique`，同一行为可跨多个战术。`tactic` 用 `initial_access`、`command_and_control` 这类下划线枚举值，编号基准见 `references/workflow_tracing.md` 步骤 5。
- 事件内容变化时证据版本递增，已登记的报告随之标为落后。校验失败时不要为通过校验改写事实，证据不足就保持 `inferred`。

快照规则：

- 定稿时调用 `case_read`，把未撤回的事件按时间顺序写入 §3。每条写 `TL` 编号、原始时间及时区、动作、状态和 `CE` 证据编号；`inferred` 事件标「推断」并写明 `reason`。
- §5 只列 `confirmed` 的 `attack` 事件，每个 `technique` 一行，证据写 `CE` 编号。
- 多份 findings 时，每份只写涉及该主机或账号的事件，同一事件保留同一 `TL` 编号；多主机合并时按 `TL` 编号去重。
- 快照写入后仍以 Case Board 为准：先改事件，再刷新 §3 和 §5，不单独改这两节。

### 证据记录

证据编号在本底稿内唯一（如 E01），跨主机引用带底稿名或 Client ID。每条证据保留：资产/账号与来源、实际命令或查询、查询时间窗、事件原始时间/时区、采集时间、关键原文、退出状态、是否截断及未读范围。工具提供查询 ID、进程启动时间或会话 ID 时一并记录；来源相同的 API、告警与截图标记同源，不重复算独立证据。

字段不可得就写「未提供」与影响，不猜测时间或完整性。完整性未知、部分返回、失败、未查和完整无命中分别记录；主机证据与委派结果用同一口径。每轮只追加改变问题裁决的证据，重复查询注明状态变化或新范围，仍有效的结果按编号复用。

## 内容结构

按以下固定章节填写；没有内容时区分已查无发现、未查、无法获取或不适用并写明原因，不统一写「无」，不要删除章节（多主机合并时按章节对位读取）：

1. **主机标识** — 完整 hostname、Client ID、公网/私网 IP、实例 ID、资产用途；云侧另记 UID/地域及映射依据，云侧事件另记受影响身份（AK ID / RAM 用户 / 角色）与涉及的云资源或域名
2. **事件定性** — 一句话定性 + 措辞等级（已确认 / 推测 / 无法确认）+ 报告严重等级（高危 / 中危 / 低危）及一句判断依据，含主要 ATT&CK 技术编号；严重等级是本次事件的最终研判，不直接照抄告警级别。本节另列影响对象、已观察到的行为及后果、时间窗、规模与统计口径、证据编号及未知边界；区分权限、尝试、读取、修改、导出和外传，多主机汇总注明去重口径，未知数量不得记为 0
3. **时间线** — 保留影响因果、范围或处置的节点，每条注明证据编号、原始时间及时区；不受正式报告节点上限限制，定稿时区分事件时间与检测/采集时间，不把 ctime 当创建时间；运行环境提供 `case_update` 时见「攻击时间线位置」
4. **入侵路径** — 按攻击阶段写已验证的步骤，每步附可独立核查的证据记录：优先日志/请求原始行（含时间戳、来源、完整接口路径或 URL、状态码），其次命令及关键输出行、文件绝对路径与时间属性；操作审计、SAS 遥测等结构化来源写出主体、对象、时间等关键字段值。不得用「access 日志可证」「进程链吻合」这类只报来源、不含内容的指针概括代替；没有命令输出时使用对应日志、文件、网络或客户确认记录，不为凑格式补命令。云侧事实有控制台截图时，在该条证据记录下加一行 `截图: <相对路径>（页面 · 账号/站点 · 截取时间）`，规则见「证据截图」
5. **ATT&CK 映射** — `T编号 :: 行为 :: 证据` 列表，只列通过步骤 7 验证门的；§4 已验证步骤体现的技术须在本节有对应条目（反向不要求，本节可含持久化等非路径技术）
6. **IoC 清单** — IP / 域名 / 文件路径 / 哈希 / 账户，记录**原始值**（展示层转义在报告里做）
7. **入口 / 漏洞** — 先写证据支持的初始入口；仅在证据指向漏洞利用时记录类型、受影响组件与版本、CVE（如有）及修复方案来源。凭证滥用、合法工具滥用、配置暴露或社会工程写实际入口并注明「未发现需要绑定的漏洞」；入口证据不足写「无法确认」，不得为完整度强行匹配 CVE
8. **残留风险** — 步骤 6 六个维度的对象与覆盖结果，分别写「已清 / 仍在 / 未观察到 / 未完成 / 不适用」及依据；「已清」需有先前阳性与后续处置/复核记录，不能把缺证据写成清除
9. **处置进展** — 先写当前事件状态，再按抑制 / 根除 / 恢复三个阶段记录已完成、进行中、未开始的动作及依据；`[x]` / `[/]` 只能来自主机证据或客户确认，未取得记录时明确写核实对象、核实方式及仍缺少的记录，不要把建议写成已执行。恢复阶段记录恢复对象、验证结果与未满足条件；责任方和期限仅记录已知信息
10. **云端证据覆盖** — 日志源、查询时间窗、最早/最新记录、保留期、覆盖限制；每项写明渠道和账号标识（`sas`/`sls` 写 UID，`aliyun` 写 profile 名，`opencli` 写 profile 别名），不写 AccessKey 值；`aliyun` 输出没有工具落盘，证据记录写 API、关键参数、执行时间和关键字段值，并在本节注明未保存原始响应；告警驱动模式另记 `$sas` 输入范围，直接详情模式记录输入的数字 `Id`，资产 / 实例列表模式记录查询时间窗与完整数字 `Id` 集合，多条结果全部保留；主机侧调查至少按网络外联、进程启动、远程/数据库登录、SAS 告警四类逐项写「覆盖或缺口 + 原因」；未查云端时写明原因
11. **验证结果** — 步骤 7 核验中被降级或删除的断言及原因
12. **证据缺口** — 想查而没查到的项，是报告「覆盖说明」的素材

## 证据截图（可选，只针对云侧事实）

- 步骤 7 验证门过完、findings 定稿前，由编排者把「已确认事实 → 待截对象」清单委派给 `opencli-aliyun-ir` 的控制台截图流程，只截通过验证的承重断言对应的云侧事实（告警详情、ActionTrail 事件、云防火墙/WAF 命中、暴露面配置）；主机侧证据走 SIREN 文本通道，不截图。多主机在全部主机过完验证门后一次委派，文件名带 Client/资产标识。
- 落盘在当前工作目录 `<报告名>.assets/`（报告名为 findings 名去掉 `.findings` 和 Client、轮次后缀），一图对应一条事实。截图挂在它佐证的证据记录下（§4 或 §7–§8），写明路径、控制台页面、账号/站点和截取时间，不单独开章节。
- 截图只佐证已有记录，不计入独立证据源（同源规则见 `references/verification_checklist.md`「因果与孤证」）；截不到不算证据缺口，报告在该处不放图。截图不打码，但不截含登录凭据、Cookie、令牌的页面。

## 结论交付层使用规则

步骤 7 的精炼调查结论同样只以 findings 为事实来源。

- 只接收状态为「已验证」的底稿，只取固定章节的事实；工作区段的待证断言和未决问题只能作为缺口披露。
- 依次写事件定性（沿用 §2 的措辞等级与严重等级）、关键证据与边界（附证据编号）、影响与残留风险（§2、§8）、处置进展（§9 当前状态）和建议动作（§9 未开始项、§7 修复方案），最后说明影响结论的能力与证据缺口（§10、§12）。
- 标题与首句不得强于 §2 定性：「推测」「无法确认」不得升级，覆盖不足的阴性判断不得写成「未失陷」「误报」「已清除」；数量、时间、IoC 和动作范围照抄 findings，不外推到未覆盖的主机、目录或账号。
- 只写结论与依据，不复述调查过程；必填项缺失时回报编排者，不补写。
