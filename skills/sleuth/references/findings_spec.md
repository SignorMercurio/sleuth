# Findings 中间文件规范（调查 → 报告的交接层）

每台主机完成步骤 2–7（含对抗式验证）后，把定稿结论落为一份 findings 文件；默认先据此向用户交付精炼调查结论，不生成正式报告。用户确认进入步骤 8 后，写作层**只以 findings 文件为事实来源**，调查上下文中未写入 findings 的内容一律不得进入报告。这一层同时服务三个目的：多主机合并的输入、报告写作（含子 agent）的自包含输入、防止未经验证的结论渗入交付内容。反过来，支撑结论的证据没有原文落进 findings，写作层就拿不到，报告只剩叙述。findings 只压结论与旁支，不压证据；篇幅取舍留给写作层。

## 文件命名

```
IR-{YYYYMMDD}-{hostname}-{event_type}[-{event_id}].findings.md
```

字段含义与 `references/report_naming.md` 一致，生成在当前工作目录，单主机也生成（N=1）。findings 是内部工作底稿，不是正式报告；默认交付物是对话中的精炼调查结论。用户确认生成报告后，正式报告交付物只有最终一份 `IR-….md`，findings 文件保留备查，去留由用户决定。

## 内容结构

按以下固定章节填写；没有内容的章节写「无」，不要删除章节（多主机合并时按章节对位读取）：

1. **主机标识** — hostname、Client ID、公网/私网 IP、实例 ID、资产用途
2. **事件定性** — 一句话定性 + 措辞等级（已确认 / 推测 / 无法确认）+ 报告严重等级（高危 / 中危 / 低危）及一句判断依据，含主要 ATT&CK 技术编号；严重等级是本次事件的最终研判，不直接照抄告警级别
3. **时间线** — 决定性节点（数量上限同报告时间线块约束），每条注明证据来源与时区
4. **入侵路径** — 按攻击阶段写已验证的步骤，每步附可独立核查的证据记录：优先日志/请求原始行（含时间戳、来源、完整接口路径或 URL、状态码），其次命令及关键输出行、文件绝对路径与时间属性；操作审计、SAS 遥测等结构化来源写出主体、对象、时间等关键字段值。不得用「access 日志可证」「进程链吻合」这类只报来源、不含内容的指针概括代替；没有命令输出时使用对应日志、文件、网络或客户确认记录，不为凑格式补命令
5. **ATT&CK 映射** — `T编号 :: 行为 :: 证据` 列表，只列通过步骤 7 验证门的；§4 已验证步骤体现的技术须在本节有对应条目（反向不要求，本节可含持久化等非路径技术）
6. **IoC 清单** — IP / 域名 / 文件路径 / 哈希 / 账户，记录**原始值**（展示层转义在报告里做）
7. **入口 / 漏洞** — 先写证据支持的初始入口；仅在证据指向漏洞利用时记录类型、受影响组件与版本、CVE（如有）及修复方案来源。凭证滥用、合法工具滥用、配置暴露或社会工程写实际入口并注明「未发现需要绑定的漏洞」；入口证据不足写「无法确认」，不得为完整度强行匹配 CVE
8. **残留风险** — 步骤 6 六个维度的结果，逐项写「已清 / 仍在 / 未观察到」
9. **处置进展** — 先写当前事件状态，再按抑制 / 根除 / 恢复三个阶段记录已完成、进行中、未开始的动作及依据；`[x]` / `[/]` 只能来自主机证据或客户确认，未取得记录时明确写「未取得处置记录」，不要把建议写成已执行
10. **云端证据覆盖** — 日志源、查询时间窗、最早/最新记录、覆盖限制；告警驱动模式另记 `$sas` 输入范围，直接详情模式记录输入的数字 `Id`，资产 / 实例列表模式记录查询时间窗与完整数字 `Id` 集合，多条结果全部保留；主机侧调查至少按网络外联、进程启动、远程/数据库登录、SAS 告警四类逐项写「覆盖或缺口 + 原因」；未查云端时写明原因
11. **验证结果** — 步骤 7 核验中被降级或删除的断言及原因
12. **证据缺口** — 想查而没查到的项，是报告「覆盖说明」的素材

## 正式报告写作层使用规则

- 仅在用户确认生成 / 合并正式报告后进入步骤 8；未确认时停在步骤 7，不复制模板、不创建 `IR-….md`。
- 写作（步骤 8）只读：全部 findings 文件、报告模板、`references/report_naming.md`、`references/report_style.md`、`references/report_writing_rules.md`、本文件。不回看调查上下文，不碰 SIREN；执行方式与降级规则见 `references/runtime_compat.md`「报告写作隔离」。
- Findings 是报告的事实边界，不是必须逐项展开的报告提纲。写作层按各章节职责选择影响定性、影响范围、证据链或客户动作的内容；常规阴性结果合并概括，不影响结论的验证记录和旁支线索留在 findings。
- 写作不得改变事实与措辞等级：「推测」不得升级为「已确认」，IoC 不得增删改，时间不得四舍五入到改变先后关系。
- 写作中发现一般证据缺口：不补写、不脑补，在报告对应位置用客户可理解的话说明，并把缺口回报给编排者，由编排者决定是否回到步骤 2–7 补查。
- 严重等级、当前事件状态或处置进展缺失时不得生成定稿，也不得在报告里写「findings 未提供」或用「无法确认」填充这些必填字段；先把缺口回报给编排者补齐。

## 多主机合并规则（多主机委托与合并模式）

合并模式（输入是用户提供的既有 `IR-….md` 报告）下，报告正文视作 findings 等价物，本文件全部规则同样生效：只做重组与改写表述，不得新增事实或升级措辞。

- **排查对象**：每台主机一个 `::: asset` 块（模板原生支持多资产）
- **时间线**：合并为一条统一时间线，节点标注主机名，节点数量上限同报告时间线约束
- **事件定性**：定性针对整个事件；各主机结论明显无关联（无共享 IoC、时间窗、手法）时仍只出一份报告，但在定性中分别陈述并写明「未发现关联」
- **ATT&CK 矩阵**：一个矩阵，任一主机有证据支撑即点亮该技术
- **技术分析**：按主机分小节，另加一节「跨主机关联分析」收纳横向移动 / 同源判断（须已过验证门）
- **响应行动**：合并去重，每条动作标注适用主机并保留各自主机 findings 中的真实状态；全局动作（如封禁攻击 IP）只写一次
- **输出文件名**：按 `references/report_naming.md` 的多主机规则生成
