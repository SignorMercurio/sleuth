# 结论对抗式验证清单（交付前质检门）

SKILL.md 步骤 7 加载本文件。目的：每条「承重断言」先经独立核验再定稿，系统化防止误归因。各 `invest_*` / `tech_*` 指南里的判读注意事项在此集中成一道强制门。

## 承重断言（逐条过门）

会写进结论或正式报告、且支撑定性或处置的断言：事件定性（什么攻击 + 是否得手）；入侵路径每一步（入口 / 执行 / 外联 / 持久化 / 处置）；每个点亮的 ATT&CK 技术；每条「攻击者做了 X」；每个 IoC 的归因；时间线关键节点（T0、止损点）；影响处置的阴性判断（据此停止排查、判定无需隔离、宣称风险已清）。过程描述不必过门；「未观察到」措辞不免检。

## 核验流程

1. 先写出实际准备交付的摘要与建议草稿，从草稿和 findings 列出全部承重断言；标题、首句和动作范围必须在列。
2. 逐条（多时按章节分组）交独立核验：运行时有子 agent 就派（映射见 `references/runtime_compat.md`），只给「断言 + 所引证据 + 本清单」，不给主 agent 的推理；无子 agent 则主 agent 换「我要推翻这条」的视角自检。核验方默认存疑、尽力反驳，可跑少量定向只读命令补证（同受只读护栏约束），不重做整轮采集。
3. 裁决：被反驳或证据不足 → 降级（「已确认」→「推测」/「无法确认」）或删除；「未观察到」只用于实际检查范围内无命中，不替代未查或失败。扛住反驳 → 保留确定措辞。
4. 产出核验表 `断言 | 裁决 | 反驳依据 | 交付措辞调整`（内部用，不进交付内容）。通过的交付草稿写入 findings 后原样发送，保留限定语与动作范围；发送时新增或加强的断言必须重新核验。

## 反驳清单

按断言类型逐条质疑。每条写的是「要有什么证据」与「没有就怎么写」。

**时间**
- `atime` ≠ 攻击者访问：扫描、备份、杀软读取都会刷新；要有 Web 日志或进程记录交叉。
- `ctime` ≠ 落地时间，mtime 早于 ctime 只是回改候选（判读见 `references/tech_process_file.md`）；不补写「用 touch 回改」等未观察到的具体动作。候选筛选须同时按 mtime 与 ctime，不能只验证已找到的文件。
- 事件时间、检测时间、入库时间分别记录（校准见 `references/tech_log_analysis.md`）；窗口无命中先查覆盖与字段语义再扩窗。

**存在 ≠ 利用 / 得手**
- 文件存在 ≠ 当前可用：查中间件配置（如 `location ~ \.php$ { return 403; }`）+ 实际访问状态码。
- 上传成功 ≠ 利用成功；SUID / 可疑二进制存在 ≠ 已用于提权，要有调用证据。
- 当前为空、无执行位、进程不在或日志无命中 ≠ 历史从未执行；HTTP 200 与响应字节数 ≠ 命令执行或数据外传。分别用历史执行记录与具体响应内容验证。

**来源归因**
- WAF / 应用来源先核代理链与字段信任（`references/tech_log_analysis.md`）；SSH 按准确会话归因（`references/ssh_login_attribution_sas.md`），不凭 PID 邻近或时间相邻归因。
- 对 WebShell 目录后来的 GET / 访问 ≠ 原始上传源，只能写「近期访问 / 探测」。
- 文件时间与某次登录或传输相近 ≠ 该会话是唯一写入者；要有该会话的操作记录，否则列为候选。
- IP 归属与信誉要外部情报佐证，不凭地域臆断。

**云端与阴性判断**
- WAF `waf_action='block'` ≠ 实际拦截：结合 `waf_test` / `final_action` / `upstream_status` / `status`；测试或观察模式不是真拦。
- 「未检出」≠「未发生」：核对日志覆盖窗是否早于攻击窗；遥测起始晚于攻击窗只能写「无法据此排除」。
- 阴性断言同时检查：资产 / 账号正确、采集完整、命令成功、过滤不过窄、无未读分页或截断；缺任一项就写明限制范围（如登录或日志样本量不足，不得据此排除暴破、登录或外联）。
- 标题、首句与处置建议和正文保持同一边界：正文承认覆盖不足，开头不能写「不是挖矿」「未失陷」「误报」。配置注释、进程名与本机发布清单也可能被改，关键可信性另行核验。
- 检测机制的解释（扫描触发、告警规则误报）只是候选，要有扫描记录或机制文档支持才能写成原因。
- OOB / DNSLog 域名命中 ≠ 主机失陷：需后续命令执行、外联、落地文件等跟进证据才能升级定性。

**因果与孤证**
- 父链 / 时间相邻先问是巧合还是因果；每个点亮的 ATT&CK 技术要有具体证据，不因「这类攻击通常会」点亮。
- 先拆开直接观察与因果推断：一条可靠来源的记录只能确认「该来源记录了 X」，不能同时确认攻击者身份、入口、执行成功与影响。
- 得手、入口、归因、跨主机关联需至少两类独立证据并排除合理替代解释；同一原始事件的告警、API、截图和转述算同源；客户确认只支持其实际确认的动作。
- 一类记录的时长不能推导另一类行为的时长（如 SSH 会话时长 ≠ C2 持续时间）。
- 核验范围不外推：单个文件的核验不能扩成目录级或供应商级加白。
- 缺失能力只限制依赖该证据的断言：已充分支持的局部事实可以确认，未覆盖范围保留缺口；不因多读一个来源自动升级整条攻击链。

## 与交付内容的衔接

核验后的措辞先用于步骤 7 的调查结论；用户确认报告后再对应到 `assets/report.md`。不确定写「未观察到 / 无法确认」，覆盖边界写进「覆盖说明」，残留风险只列证据支持的项。
