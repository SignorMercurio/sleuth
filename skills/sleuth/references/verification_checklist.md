# 结论对抗式验证清单（交付前质检门）

SKILL.md 步骤 7 在交付调查结论前加载本文件。目的：把将向用户交付或可能写入正式报告的每条「承重断言」交给独立核验后再定稿，系统化防止**误归因**——本领域最大的交付风险。清单条目本身来自各 `invest_*` / `tech_*` 指南里散落的判读注意事项，这里集中成一道强制门。

## 承重断言（必须逐条过门）

会写进调查结论或正式报告、且支撑定性或处置的结论：

- 事件定性（是什么攻击 + 是否得手）
- 入侵路径的每一步（入口 / 执行 / 外联 / 持久化 / 处置）
- `::: attack` 矩阵每个点亮的技术
- 每条「攻击者做了 X」的行为结论
- 每个 IoC 的归因（某 IP / 文件 / 进程属于攻击者）
- 时间线的关键节点（T0、止损点）
- 会影响处置的阴性判断（如据此停止排查、判定无需隔离或宣称风险已清）

非承重的过程描述不必逐条过门；不能仅因使用「未观察到」措辞就免检影响决策的断言。

## 核验方式

1. 先形成实际准备交付的摘要与建议草稿，再从草稿和 findings 中列出全部承重断言；核验对象必须包含最终标题、首句和动作范围。
2. 逐条（断言多时按报告章节分组）派**独立核验 agent**：
   - 运行时支持子 agent 就派（见 `references/runtime_compat.md` 的派生子 agent 映射）；只给该 agent「断言 + 所引证据 + 本清单」，**不给主 agent 的推理过程**，避免确认偏误。
   - 运行时不提供子 agent，则主 agent 换「我要推翻这条」的怀疑视角逐条自检。
   - 核验 agent 默认存疑，任务是**尽力反驳**；必要时可跑少量定向只读命令补证（如查中间件配置、日志覆盖窗），但不重做整轮采集，且同受只读护栏约束。
3. 裁决并改写交付措辞：
   - 被成功反驳或缺少该断言所需证据 → 降级（「已确认」→「推测」/「无法确认」）或删除；「未观察到」仅用于实际检查范围内无命中，不替代未查或失败。
   - 扛住反驳 → 保留确定措辞。
4. 产出核验表（内部用，不进用户交付内容）：`断言 | 裁决 | 反驳依据 | 交付措辞调整`。将通过核验的交付草稿写入 findings 后再发送，保留限定语与动作范围；发送时新增或加强的断言必须重新核验，不能绕过裁决自由重写摘要。

## 反驳清单（逐类质疑）

**时间证据**
- `atime` 不等于攻击者访问——云安全中心 / SAS 扫描、备份、杀软读取都会刷新；要有 Web 日志或进程遥测交叉。
- 时间窗、mtime/ctime 与告警延迟分别按 `references/tech_process_file.md`、`references/tech_log_analysis.md` 核验；特别检查候选筛选是否漏掉回改 mtime 的文件，不能只验证已找到的文件。

**存在 ≠ 利用 / 得手**
- WebShell / 后门文件存在 ≠ 当前可用：查中间件配置（如 `location ~ \.php$ { return 403; }`）+ 实际访问状态码。
- SUID / 可疑二进制存在 ≠ 已被用于提权：要有调用证据。
- 文件落地 ≠ 攻击成功：区分「上传成功」与「利用成功」。
- 当前为空、无执行位、进程不存在或日志无命中，不能反推历史从未执行；HTTP 200 与响应字节数也不能单独证明命令执行或数据外传。用历史执行记录与具体响应内容分别验证。

**IP / 来源归因**
- WAF/应用来源先按 `references/tech_log_analysis.md` 核验代理链与字段信任；SSH 按 `references/ssh_login_attribution_sas.md` 核验准确会话，不凭 PID 邻近归因。
- 对 WebShell 目录后来的 GET / 访问 ≠ 原始上传源 IP，只能写「近期访问 / 探测」。
- IP 归属与信誉要外部情报佐证，别凭地域臆断。

**云端措辞**
- WAF `waf_action='block'` ≠ 实际拦截：结合 `waf_test` / `final_action` / `upstream_status` / `status` 判断，test / 观察模式不是真拦。
- 「未检出」≠「未发生」：必须核对日志覆盖时间窗是否早于攻击窗口；遥测起始晚于攻击窗时只能写「无法据此排除」。
- 对阴性断言同时检查：目标资产/账号是否正确、采集是否完整、命令是否成功、过滤条件是否过窄、分页/截断是否仍有未读结果；缺任一项就明确限制范围。
- 首句、标题和处置建议必须保持同样边界，不能正文承认覆盖不足，开头却写「不是挖矿」「未失陷」或建议直接加白；配置注释、进程名与本机发布清单也可能被改，关键可信性须另行核验。

**OOB / DNSLog**
- DNS / OOB 域名命中 ≠ 主机失陷：需后续命令执行、外联、落地文件等跟进证据才能升级定性。

**因果与孤证**
- 进程父链 / 时间相邻是巧合还是因果？父链命中要能解释行为。
- 每个点亮的 ATT&CK 技术要有具体证据，不能因为「这类攻击通常会」就点亮。
- 先拆开直接观察与因果推断。一条来源可靠、范围与完整性已核对的记录可确认「该来源记录了 X」，不能据此同时确认攻击者身份、入口、执行成功与影响。
- 得手、入口、攻击者归因、跨主机关联等因果断言仍需至少两类独立证据相互支持，并排除合理替代解释；仅孤证或相关性不足则降级。工具数量不是证据数量：同一原始事件的告警、API、截图和转述都算同源；客户确认只能支持其实际确认的动作。
- 缺失能力只限制依赖该证据的断言。其他可核查证据已充分支持的局部事实可以确认，未覆盖的范围继续保留缺口；不得因多读一个来源自动升级整条攻击链。

## 与交付内容的衔接

核验后的措辞先用于步骤 7 的调查结论；用户确认生成正式报告后，再对应到 `assets/report.md`。不确定写「未观察到 / 无法确认」，覆盖边界写进「覆盖说明」，残留风险只列证据支持的项。
